# Рефакторинг SSR и асинхронных данных – 2026-09-28

Правила закреплены в `architecture.md` → «Политика асинхронных данных». Здесь –
что было, что сделано, чем проверено.

## 1. Стратегия данных

- Чтение – только `useAsyncData` + метод сервиса. `useFetch` не используется
  (обошёл бы `useApi` с токенами и refresh), `$fetch` – только внутри `useApi`.
- Три класса данных: основные (в SSR, скелетон, `UiErrorState`), вторичные (в SSR,
  скелетон, деградация в пустое состояние), только клиент (`server: false`, всё с
  токеном).
- Ключи `<домен>[:<ресурс>][:<параметры>]`, один ключ – один запрос с одним смыслом.

## 2. `await`

Было 7 `await useAsyncData`, стало **0**. Ни в одном месте код после `await` не
зависел от данных – он только блокировал переход по клику.

| Где                          | Было                                | Стало                                                  |
| ---------------------------- | ----------------------------------- | ------------------------------------------------------ |
| `pages/clubs.vue`            | `await`, ключ `clubs`               | без `await`, ключ `activities`, скелетон в `ClubsList` |
| `pages/teachers.vue`         | `await`                             | без `await` (скелетон был)                             |
| `pages/gallery.vue`          | `await` + ручное накопление страниц | `usePagedList(..., { server: true })`                  |
| `clubs/Schedule.vue`         | `await`, `clubs-schedule:<неделя>`  | без `await`, `schedule:week:<неделя>`                  |
| `home/top-clubs/Section.vue` | `await`, `popular-clubs`            | без `await`, `activities:popular`, скелетон            |
| `home/events/Section.vue`    | `await`, `home-events`              | без `await`, `events`, скелетон                        |
| `home/gallery/Section.vue`   | `await`, `home-gallery`             | без `await`, `gallery:home` (лимит 5), скелетон        |

`await` вернётся только там, где код после вызова нуждается в данных
(SEO-мета сущности, `createError(404)`) – сейчас таких страниц нет.

## 3. SSR

Не изменился по содержанию: Nuxt дожидается `useAsyncData` на сервере и без
`await` (дока 4.4, «A note on `await`»). Проверено `curl` по `/`, `/clubs`,
`/teachers`, `/gallery`, `/enroll/*`: данные в HTML, ключи в payload, скелетонов
(`aria-busy`) в серверном HTML – 0.

Единственное место, где простое снятие `await` сломало бы SSR, – галерея: `photos`
копировались из `data.value` один раз в `setup`, а `watch` на сервере не срабатывает.
Переведена на `usePagedList` (опция `server` добавлена, по умолчанию `false` –
кабинет не затронут).

## 4. Клиентская навигация

Было: клик → старая страница замерла без индикации → новая появляется после ответа
API (на `/clubs` – после двух ответов подряд).

Стало: клик → сразу каркас новой страницы со скелетонами → данные. Замер с
искусственной задержкой API 800–2500 мс: `/about → /clubs` – через 300 мс на
`/clubs`, 16 скелетон-блоков; `/about → /enroll/trial` – через 700 мс, 10 блоков.

## 5. Загрузка

- `<NuxtLoadingIndicator>` в `app.vue` – чанки роутов, middleware, иконки.
- Скелетоны добавлены: `ClubsList`, три секции главной, расписание на десктопе

- Ошибка расписания – `UiErrorState` вместо ручной вёрстки.
- `/me`: общий `isProcessing` (любой запрос → пульсируют все виджеты) заменён на

## 6. Запросы

- **Каскад `/clubs`**: страница ждала каталог, потом монтировался `Schedule` и
  запрашивал расписание. Теперь оба стартуют в одном тике (158/167 мс при
  задержке 800 мс, окончание 962/984 мс).
- **Каскад `/enroll/trial`**: слоты ждали каталог (ключ от выбранного кружка).
  Теперь ключ `trial-slots:<id из URL>` известен в `setup` – запросы параллельны.
- **Ключи**: `activities` (было `clubs` + `enrollment:trial:clubs`), `events`
  (`home-events` + `enrollment:events`), `me-profile` (`me-profile` +
  `checkout-profile`). Честно: в Nuxt 4 данные ключа удаляются, когда размонтирован
  последний потребитель, так что между страницами запросов меньше не стало. Выигрыш –
  общий кэш при одновременных потребителях и `clearNuxtData("me-profile")` после
  анкеты, который теперь сбрасывает и профиль чекаута (раньше не сбрасывал).

## 7. Гидрация

- **`/enroll/trial?clubId=3`** – 8 mismatch'ей (карточка кружка, слоты, сводка,
  CTA): выбор чинился `watch`'ем после загрузки каталога, а на сервере `watch` на
  догрузку не реагирует. Выбор кружка и слота теперь `computed` от «запрошенного»
  и данных; синхронизация URL следит за запрошенным, а не выведенным (иначе
  `slotId` пропадал из URL, пока грузились слоты). Проверено: свободный слот из
  ссылки выбран, занятый – снят и убран из URL, `clubId=999` – очищен, смена
  кружка сбрасывает слот.
- **`Set operation on key "value" failed: target is readonly`** на каждой SSR-странице:
  стор `auth` отдавал `readonly(secondsLeft)`, Pinia считала его state и на
  гидрации писала в него значение из payload. Отдаётся `computed` (getter).

## 8. Исключения

- `enrollment:subscription-schedule` (`getWeek()` без недели) не объединён с
  `schedule:week:<неделя>`: эквивалентность «без параметра = текущая неделя» у бэка
  не подтверждена.
- `/enroll/trial?clubId=<slug>`: ключ слотов известен только после каталога, при
  прямом заходе возможен mismatch. Ссылки со slug приложение не генерирует
  (`clubs/Card.vue` даёт числовой id), поддержка оставлена как фолбэк.
- Очистка невалидных `clubId/slotId/eventId` из URL – только при прямом заходе
  (`onMounted` с данными из payload); при переходе по клику невалидный параметр
  просто не выбирается.
- `/login`, `/me` – `ssr: false` намеренно (токены в localStorage).

## 10. Правила для нового кода

1. Данные – `useAsyncData(key, () => svc.method())`, без `await`.
2. `await` – только если следующая строка `setup` читает `data`; причина – в комментарии.
3. Секция показывает скелетон по своему `pending` и только пока данных нет.
4. Ошибка основной секции – `UiErrorState` с `retry`; вторичной – пустое состояние.
5. Ключ отражает все параметры запроса; одинаковый вызов – одинаковый ключ.
6. Зависимый запрос – от исходного параметра (URL, prop), не от результата другого.
7. Выбор, валидируемый по данным, – `computed`, не `watch`.
8. Никаких значений в `setup`, скопированных из `data.value` один раз.
9. Токены и браузерные API – `server: false` / `onMounted`, не ради скорости.
10. В Pinia setup-store наружу – `ref` (state) или `computed` (getter), не `readonly`.
