## 1. Конвенция моков (действует для обеих задач)

Цель – удалить мок и подключить бэк правкой в одном месте, без затрагивания UI.

1. **Мок живёт только в сервисном слое.** Файлы – `app/services/mocks/*.mock.ts`
   (подпапка не попадает в автоимпорт `imports.dirs: ["services"]`, импорт явный).
   Компоненты, композаблы, страницы и `types/` про мок не знают.
2. **Доменные типы постоянные**, лежат в `~/types/index.ts` (`MeBooking`, `MeProfile.isComplete`).
   Компоненты работают только с ними, как и с живыми данными.
3. **Черновик DTO – внутри файла мока**, не в `types/` и не в `api.d.ts`. Он
   повторяет ожидаемую форму ответа (snake_case, копейки) – тогда маппер
   `toBooking` пишется сразу и переживает интеграцию.
4. **Маркер `MOCK(<id>)`** в каждом месте, где мок подключён (import, тело метода).
   `rg "MOCK\(" app` – чек-лист удаления. Идентификаторы: `bookings`, `profile-referral`.
5. **Мок имитирует задержку** (~400 мс), иначе скелетоны и `loading` не проверить.
6. **Перед запуском проекта `rg "MOCK\(" app` должен быть пуст.** Мок виден на
   `preprod` – осознанно принято на время разработки. Строка про это – в техдолг трекера.

Как выглядит место подключения:

```ts
// Одна строка комментария о назначении, как везде.
async getBookings(): Promise<MeBooking[]> {
    // MOCK(bookings): заменить на this.fetch<BookingItem[]>("/v1/me/bookings/")
    const items = await mockBookings()
    return items.map(toBooking)
}
```

## 2. Задача A – анкета на `/login`

### 2.1 Поведение

```
email → код → verify ──► GET /me/profile/
                          ├─ isComplete  → /me
                          └─ !isComplete → шаг «profile» (анкета) → PATCH → /me
```

- Анкета показывается вместо блока «email / код» на той же странице `/login`.
- Бросил на анкете и вернулся: токены есть, профиль пуст → `/login` снова показывает анкету, не `/me`.
- Прямой заход на `/me` с токеном, но пустым профилем → редирект на `/login` (гейт).
- Критерий «профиль пуст» – **временно** `!full_name?.trim()`, одна функция
  `isProfileComplete(dto)` в `me.service.ts`. Настоящий контракт – открытый вопрос 10;
  когда решится, меняется только эта функция.

### 2.2 Поля и схема

| Поле                   | Обязательность | Правило                                                                 |
| ---------------------- | -------------- | ----------------------------------------------------------------------- |
| ФИО                    | да             | `fields.fullName`                                                       |
| Почта                  | –              | из стора `auth`, `disabled`, в схему и payload не входит                |
| Телефон                | нет            | новое `fields.phoneOptional`: пусто **или** полная маска `Maskas.Phone` |
| Откуда вы о нас узнали | да             | `z.string().min(1, …)`, `USelect` из `constants/referral-sources.ts`    |

Список источников уже есть копией в `event/RegistrationForm.vue` (`referralItems`).
Выносим в `app/constants/referral-sources.ts`, оба места импортируют константу.
Новое общее правило `phoneOptional` – в `schemas/fields.ts`, не копией в схему.

Подводные места:

- Сейчас `login.vue` уходит на `/me`, как только `isAuthed` – это надо развести
  с шагом `profile`, иначе анкета не покажется никогда.
- После успешного PATCH инвалидировать `me-profile` (`refreshNuxtData`), иначе
  гейт возьмёт закэшированный «пустой» профиль и вернёт на `/login`.
- Если `GET /me/profile/` упал сразу после `verify` – не блокировать вход:
  `accepted`, окончательную проверку сделает гейт на `/me`.
- `redirectFrom` в проекте ещё не реализован (`architecture.md` §5.2) – вне
  скоупа, но шаг `profile` не должен мешать добавить его потом.
- `GuestGate` уже нарушает контракт компонентов (function-props, аудит §3.3) –
  не расширять его, анкета в отдельном компоненте.

### 2.4 Валидация: только при сабмите, ошибки чистятся при вводе

Механика (сверено с Nuxt UI 4.6):

- `<UForm :schema :state :validate-on="[]">` – пустой массив отключает
  blur/change/input-валидацию, сабмит валидирует всегда.
- Авто-очистки ошибок при `validate-on="[]"` **нет** – форма чистит только через
  повторную валидацию. Поэтому у каждого поля `@update:model-value="clearError('<name>')"`,
  внутри `form.value?.clear(name)` (метод `clear(name?)` есть в API формы).
  Чистится только ошибка изменённого поля, остальные остаются.
- `@error` формы: сфокусировать первое ошибочное поле –
  `document.getElementById(event.errors[0].id)?.focus()`. `FormErrorWithId.id` есть
  в типах. Форма короткая, `scrollToFirstError` из глобальных правил не нужен.
- Проверить в браузере, что ввод через `v-maska` на телефоне вызывает
  `update:modelValue` (иначе ошибка телефона не очистится).

### 2.5 Приёмка

Локальный бэк, код OTP берётся из БД (команда – `progress-tracker.md`, «Заметки»).
Новая почта создаёт `Parent` с пустым профилем – это и есть кейс анкеты.

1. Новая почта → код → показана анкета, почта нередактируемая.
2. Пустой сабмит → ошибки под ФИО и «Откуда узнали»; до сабмита при вводе и blur ошибок нет.
3. Ввод в поле с ошибкой – его ошибка исчезает сразу, остальные остаются.
4. ФИО с цифрами – ошибка. Телефон `+7 (9` – ошибка. Пустой телефон – проходит.
5. Валидный сабмит → `PATCH` → `/me`, приветствие с именем; в БД `full_name`, `phone` сохранились. Проверить, что маска телефона принимается `PhoneNumberField(region="RU")`.
6. Закрыть вкладку на анкете, снова `/login` → анкета. `/me` напрямую → редирект на `/login`.
7. Почта с заполненным профилем (`kirill-io3@yandex.ru`) → сразу `/me`, анкеты нет.
8. Ширина 375 px, клавиатурная навигация, фокус на первом ошибочном поле.
9. `bun run check` проходит. Браузерная проверка – по `ai-workflow-rules.md` §7.

## 3. Задача B – столбец «Наши записи» на `/me`

### 3.1 Что показываем

Пробные занятия и события родителя одним списком, по дате. Визуальный язык –
как у карточек абонементов. `MeActivityTypeBadge` уже умеет `trial` и `event` –
переиспользуем. Макета карточки нет: проектируется при реализации
(`ui-context.md` §10). Только то, что есть в DTO-черновике, лишних полей не выдумывать.

### 3.2 Модель и черновик DTO

Постоянная доменная модель (`~/types/index.ts`):

```ts
export interface MeBooking {
    id: string
    kind: "trial" | "event"
    title: string // кружок или название события
    subtitle: string // группа; у события пусто
    participant: string // ребёнок (пробное) или число мест (событие) – уточнить в Q11
    displayDate: string // "31.12.2001", как у MeUpcoming
    displayTime: string // "16:00-17:00"
    price: number // рубли
}
```

Черновик DTO (`services/mocks/me-bookings.mock.ts`, **гипотеза**, форма взята из
`UpcomingItem` и `api-core-contracts.md` «Лента занятий»):
`{ kind: "TRIAL" | "EVENT", source_id, date, time, student_name, activity_name, group_name, title, attendees_count, purchase_price }`.
Цена в копейках – маппер обязан пройти через `kopecksToRubles`.

Мок – 7–8 записей, чтобы проверялся «Показать ещё»: пробные и события вперемешку,
разные даты (в том числе с одним днём у двух записей), событие без `group_name`.

## 4. Порядок и разбиение

1. **Сессия A – анкета.** Внутри порциями: схемы, константа и `phoneOptional` →
   сервис и типы → стор и композабл → форма и страница → гейт в middleware → копирайт.
   Проверка после каждой порции. Гейт (middleware) можно отложить отдельным шагом,
   если сессия разрастётся, – но не забывать: без него `/me` открывается мимо анкеты.
2. **Сессия B – записи.** Порциями: тип и мок → сервис и композабл → карточка и
   список → раскладка `me.vue`.
3. A и B друг от друга не зависят и трогают разные файлы, кроме `me.service.ts`
   и `types/index.ts` – при параллельной работе развести по веткам.
