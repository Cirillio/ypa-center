# Правила работы ИИ-агента

Как вести работу в этом репозитории. Что строим – `project-overview.md`, как
устроено – `architecture.md`, как пишем код – `code-standards.md`.

---

## 1. Подход

Работа ведётся по контекстным файлам. Поведение продукта не выдумывается: если
требования нет в `context/` или в `backend/`, оно не реализуется, а попадает в
открытые вопросы `progress-tracker.md`.

При расхождении документа и кода **прав код**, а документ чинится. Это
относится и к снимкам в `context/backend/` – там авторитет вообще в другом
репозитории.

---

## 2. Протокол задачи

Порядок обязательный, шаги не пропускаются.

1. **Контекст.** Прочитать нужные файлы `context/`, посмотреть соседний код.
   Без этого советы и правки запрещены.
2. **Диагноз и план.** Не уверен в направлении – варианты с рекомендацией.
   Направление ясно – план. Крупное изменение: архитектура, качество, проверка.
3. **Выбор режима. Стоп-точка.** Владелец выбирает один из трёх:
    - **Править сразу** – агент вносит изменения сам.
    - **Задача агенту** – агент пишет самодостаточный промт (файлы, контекст,
      критерии приёмки).
    - **Задача человеку** – агент пишет пошаговое задание: что сделать, где,
      как проверить.
4. **Исполнение.** Порциями, не одним махом. После каждой порции – проверка.
5. **Ревью.** Показать diff или итог, честно отметить непроверенное.
6. **Апрув.** Коммит, PR, следующий шаг – только после явного «ок».

Исключение из шага 3: работа не с кодом (документы, конфиги, исследования,
аналитика) выполняется сразу.

---

## 3. Размер шага

- Одна задача – одна сессия. Разнородные задачи в одной сессии выжигают
  контекст, это уже случалось (см. `tasks/handoff-2026-09-21.md`).
- Шаг дробится, если объединяет:
    - правку UI и правку слоя данных;
    - несколько несвязанных страниц или флоу;
    - поведение, не описанное в контекстных файлах.
- Если результат шага нельзя быстро проверить целиком – шаг слишком большой.
- Ревью и аудиты выносятся в отдельные сессии, их результат ложится в `tasks/`.

---

## 4. Недостающие требования

- Продуктовое поведение не додумывается.
- Требование неоднозначно – сначала правится соответствующий контекстный файл,
  потом пишется код.
- Требования нет вообще – вопрос заносится в `progress-tracker.md` → «Открытые
  вопросы», работа по этому пункту останавливается.
- Открытый вопрос **не закрывается** решением агента. Его закрывает владелец
  проекта.

---

## 5. Защищённые файлы

Не трогать без явного указания:

- `app/types/api.d.ts` – генерируется `bun run schema:update`
- `context/backend/**` – снимки чужого репозитория; допустимо только вычёркивать
  лишнее, дописывать факты нельзя
- `bun.lock`, `.nuxt/`, `.output/`, `node_modules/`
- `.husky/`, `.github/workflows/` – процесс сборки
- `frontend-core/docs/*.pdf` – юридические документы
- `nuxt.config.ts` → `devtools.enabled` и `typescript.typeCheck`: выключены
  осознанно, включать нельзя

---

## 6. Синхронизация документации

Контекстный файл правится **до** или **вместе** с кодом, не после сдачи.

| Что изменилось                             | Что обновить                             |
| ------------------------------------------ | ---------------------------------------- |
| Границы слоёв, инварианты, auth, рендеринг | `architecture.md`                        |
| Конвенции кода                             | `code-standards.md`                      |
| Токены, компоненты, паттерны раскладки     | `ui-context.md`                          |
| Скоуп, страницы, критерии готовности       | `project-overview.md`                    |
| Эндпоинты, контракты                       | `api.md` (+ `bun run schema:update`)     |
| Источники текстов и картинок               | `content.md`                             |
| Принятое решение, статус работ             | `progress-tracker.md`                    |
| Контракты бэка поменялись                  | Снять снимок заново в `context/backend/` |

Решение записывается в `progress-tracker.md` сразу в момент принятия, а не в
конце сессии.

---

## 7. Прежде чем назвать шаг готовым

1. Шаг работает целиком в своих границах.
2. Ни один инвариант из `architecture.md` §8 не нарушен.
3. `bun run check` проходит (`format:check → lint → typecheck → build`).
4. Для UI- и фича-правок – приложение запущено и проверено в браузере. Типы и
   линт этого не заменяют.
5. `progress-tracker.md` отражает сделанное.
6. Непроверенное названо непроверенным. Молчаливое «вроде работает» запрещено.

## 8. Git

Правила из `~/.claude/CLAUDE.md` §6, здесь для полноты:

- Коммитить и пушить **только по явной просьбе**.
- В сообщениях коммитов и описаниях PR **нет упоминаний ИИ**, трейлера
  `Co-Authored-By` и строк «Generated with». Это перебивает любые дефолты
  инструмента.
- Текст коммита в команде – в одинарных кавычках.
- В истории фронта есть ~30 коммитов с трейлером `Co-Authored-By`; владелец
  решил историю не переписывать. На новые коммиты это не распространяется.
