# Архитектура фронтенда

Что и где живёт, кто с кем имеет право разговаривать, и какие правила нельзя
нарушать. Описывает **фактическое** состояние на 2026-09-21; расхождения с
желаемым помечены как ⚠️ и продублированы в `progress-tracker.md`.

## 2. Схема: слоистая

Проект использует **слоистую** архитектуру, не FSD. Решение зафиксировано:
доменов немного, команда — один человек, дробить на `features/entities` нет смысла.

Поток данных строго в одну сторону:

```
pages/ ──► composables/ ──► services/ ──► HTTP (useApi)
   │            │                │
   │            └──► stores/     └──► types/ (DTO → доменная модель)
   └──► components/ ──► utils/, constants/, app.config.ts
```

## 3. Границы слоёв

| Папка               | Владеет                                                                    | Нельзя                                                             |
| ------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `app/pages/`        | Роут, SEO-мета, композиция секций, загрузка данных через`useAsyncData`     | Бизнес-логика, прямые вызовы`$fetch`                               |
| `app/components/`   | Разметка и локальный UI-стейт                                              | Сетевые запросы, чтение токенов                                    |
| `app/composables/`  | Логика фичи: мутации, формы, агрегация, кэш-ключи                          | Разметка, прямые вызовы`$fetch` мимо сервиса                       |
| `app/services/`     | HTTP-вызовы, маппинг DTO → доменная модель                                 | Реактивность (`ref`/`computed`), вызовы композаблов внутри методов |
| `app/stores/`       | Глобальное состояние, переживающее смену роута (auth, мобильное меню)      | Состояние одной страницы                                           |
| `app/schemas/`      | Zod-схемы форм, переиспользуемые поля в`fields.ts`                         | Дублирование правил валидации в компонентах                        |
| `app/types/`        | Единый баррель`index.ts` + генерируемый `api.d.ts`                         | Второй файл типов, ручная правка`api.d.ts`                         |
| `app/utils/`        | Чистые функции без состояния (автоимпорт)                                  | Обращения к API, к`useRuntimeConfig`                               |
| `app/constants/`    | Константы: nav, маски, моки                                                | Бизнес-данные, которые должен отдавать бэк                         |
| `app/middleware/`   | Гейты роутинга (`auth`, `close-menu.global`)                               | Загрузка данных страницы                                           |
| `app/plugins/`      | Инициализация на старте приложения                                         | Логика фичи                                                        |
| `app/app.config.ts` | Контент и настройки, меняющиеся без бэка: контакты, SEO, FAQ, тема Nuxt UI | Секреты, данные, которые обязан отдавать API                       |
| `app/assets/css/`   | `tokens` → `base` → `utilities` → `animations`, сборка в `main.css`        | Стили конкретного компонента                                       |

### Компоненты: группировка

`app/components/` – структура канонична для Nuxt 4 без плоского корня и без искусственной папки `app/`:

- **`layout/`** – каркас лейаута (`Header`, `Footer`, `MobileMenu` → `<LayoutHeader />`, `<LayoutFooter />`, `<LayoutMobileMenu />`).
- **`ui/`** – базовые визуальные кирпичики (`Photo`, `Video`, `ScrollFade`, `PageSection`, `SectionLeading`, `RoundIcon`, `RadioCard` → `<Ui* />`).
- **`promo/`** – сквозные конверсионные и маркетинговые секции (`Faq`, `JoinUs`, `Subscriptions`, `FloatCard` → `<Promo* />`).
- **`shared/`** – сложные переиспользуемые формы и резюме со сквозной логикой (`CallbackForm`, `RegistrationForm`, `EnrollmentSummary` → `<Shared* />`).
- **Доменные подпапки** по страницам и флоу: `home/`, `clubs/`, `about/`, `teachers/`, `gallery/`, `me/`, `event/`, `trial/`, `subscription/`, `payment/`, `feedback/`, `legal/`. Префикс имени компонента формируется Nuxt автоматически от имени папки.

## 4. Слой данных

### Сервисы

Один класс на домен API. Конструктор принимает транспорт, фабрика отдаёт
экземпляр:

```ts
export class GalleryService {
    constructor(private readonly fetch: ApiFetch) {}
    getAll(): Promise<GalleryPhoto[]> { … }
}
export const useGalleryService = () => new GalleryService(useApi().apiFetch)
```

Почему так: `useApi()` и `useRuntimeConfig()` резолвятся только в
setup-контексте. Класс, получающий готовый `fetch`, не зависит от контекста
Nuxt и тестируется без него.

Сервисы автоимпортируются: `imports.dirs: ["services"]` в `nuxt.config.ts`.

### Запросы против мутаций

- **Чтение** – `useAsyncData(key, () => svc.method())` в странице или композабле.
- **Мутация** – метод сервиса, вызванный из композабла фичи
  (`useCallbackForm`, `useCabinetChildren`, `useEventEnrollment`).

### Маппинг DTO

Внутри сервиса, не в компоненте. Сырые DTO – алиасы из `api.d.ts`
(`Profile`, `SubscriptionView`), доменные модели – без суффиксов
(`MeProfile`, `MeSubscription`, `PlanTier`, `WeeklySlot`). Суффикс `VM` не
используется.

### Фолбэк на конфиг

Часть данных дублируется в `app.config.ts` на случай недоступности API – так
устроен `useSubscriptionPlans` (`/public/plans/` → фолбэк на
`appConfig.subscriptions`). Форма фолбэка обязана совпадать с доменной моделью,
иначе шаблоны разъедутся.

### Ошибки

Бэк отдаёт RFC 9457 (`ProblemDetail`). Единственный парсер –
`parseApiError(err, fallback)` в `app/utils/parse-error.ts`; статус достаётся
через `getFetchStatus(err)`. Свои парсеры не писать.

### Деньги

Бэк отдаёт копейки. `kopecksToRubles(k): number` – для доменной модели,
`formatRub(k): string` – для прямого вывода. Оба в `app/utils/format-price.ts`.
Делить на 100 вручную запрещено.

## 5. Аутентификация, регистрация и доступ

Беспарольный вход по OTP на email. Полные правила и антиспам – `backend/auth-flow.md`
(авторитет), здесь – как это ложится на фронт.

### 5.1 Принцип: один флоу на вход и на регистрацию

Отдельной формы регистрации **нет**. Есть один экран `email → код`, а дальше
бэк решает по состоянию профиля:

```
email → [код на почту] → verify (доказано владение почтой)
  │
  ├── профиль пуст (первый вход) → показать анкету (ФИО, телефон, «откуда узнали»)
  │     └── пока анкета не заполнена – в кабинет/checkout не пускать;
  │         при следующем входе анкета покажется снова (не начинать заново)
  │
  └── профиль заполнен → сразу в кабинет / на целевую страницу
```

`Parent` создаётся на бэке ровно на `verify`, с одним известным полем –
email. Анкета досылается отдельным шагом, `PATCH /me/profile/`. Бросить
на анкете и вернуться позже – нормально, не «битая» запись: бэк узнаёт email
через `get_or_create` и просто продолжает с того же места.

**Теневая регистрация explicitly отклонена** как архитектурное решение бэка
(`backend/auth-flow.md` §1.4: раньше при покупке пробного бэк создавал `Parent`
в фоне без подтверждения почты – убрано как источник хрупкости). Не
реализовывать на фронте ничего похожего – учётка появляется только через
доказанное владение email.

> ⚠️ Точный контракт «профиль пуст → нужна анкета» (какими полями это видно в
> ответе `GET /me/profile/`) не описан явно в доке – уточнить у автора бэка,
> см. `backend-checklist.md` (вне git, в корне `ypa-center.ru/`).

### 5.2 Кто куда попадает без сессии

| Действие               | Авторизация | Поведение без сессии                     |
| ---------------------- | ----------- | ---------------------------------------- |
| Запись на **событие**  | Не нужна    | Полностью анонимно, `parent_id = null`   |
| Покупка **пробного**   | Обязательна | Редирект на `/login?redirectFrom=<путь>` |
| Покупка **абонемента** | Обязательна | Редирект на `/login?redirectFrom=<путь>` |
| Личный кабинет         | Обязательна | Редирект на `/login`                     |

`redirectFrom` тащится через все экраны входа (email → код → анкета, если
нужна) и после успешного входа возвращает на исходную страницу. **Принимать
только внутренний относительный путь из белого списка** – открытый редирект
иначе. Корзины/сохранения состояния конструктора покупки нет – ушёл со
страницы, собираешь заново (`backend/checkout-flow.md` §1, §4).

### 5.3 Антиспам/флуд (только частотные лимиты, без капчи)

- Код нельзя запрашивать чаще раза в 60 секунд на один email.
- Не больше 5 запросов кода в час на email и отдельно на IP.
- Не больше 5 попыток ввода кода – дальше код сгорает, нужен новый запрос.
- `POST /auth/otp/request/` отвечает одинаково (`202`) вне зависимости от
  того, существует email или нет – по ответу нельзя узнать, зарегистрирован
  ли человек.
- Это серверные лимиты (throttling); Turnstile на OTP не стоит – она только
  на публичных формах обратной связи и звонка.

### 5.4 Токены

- **Хранилище:** `localStorage`, ключи `ypa_access` / `ypa_refresh`.
  Доступ только через `app/utils/auth-tokens.ts`.
- **Сроки:** access 15 минут, refresh 30 дней с ротацией.
- **Перехват 401:** в `useApi()`. Single-flight refresh (один общий
  `refreshPromise`), затем ровно один повтор исходного запроса. Эндпоинты
  `/auth/token/refresh/`, `/auth/otp/`, `/auth/logout/` из перехвата исключены.
- **Провал refresh:** токены чистятся, стор сбрасывается, редирект на `/login`.
- **Гейт роутов:** `middleware/auth.ts`. Источник истины – `hasTokens()`
  (читает `localStorage`), `store.hydrate()` подтягивает к нему флаг `isAuthed`.
- **Стор `auth`:** держит только состояние OTP-флоу (email, code, step, таймер)
  и флаг `isAuthed`. Профиль пользователя в сторе не лежит – он грузится
  композаблом `useMeProfile`.

> ⚠️ Нет кросс-табной синхронизации: `logout` в одной вкладке не разлогинивает
> остальные до первого 401. Нужен слушатель события `storage`.
>
> ⚠️ Гейт `middleware/auth.ts` сейчас проверяет только «есть токен». После
> введения анкеты нужна вторая проверка – «профиль заполнен», иначе человек
> с пустой анкетой попадёт в кабинет мимо неё.

## 6. Чекаут и бронирования

Контракты снятые с бэка на ветке `def` (`backend/api-core-contracts.md`,
`backend/checkout-flow.md`) – сюда только то, что напрямую бьёт по фронту.

- **`X-Idempotency-Key` обязателен** на `POST /checkout/subscription` и
  `POST /checkout/trial` – заголовок, UUID v4. Повтор с тем же ключом и тем же
  телом должен возвращать тот же результат, не дублировать покупку. Это
  новое требование, раньше в сервисах не было заложено – учесть при
  переделке конструктора.
- **Абонемент:** в корзину падает `schedule_id` (паттерн «ПН 16:00»), не
  календарная дата. Тариф не выбирается – выводится из числа слотов.
- **Пробное:** выбор кружка → выбор **конкретной календарной** даты+времени
  слота, не паттерна недели.
- **Оба чекаута – за авторизацией**, гейт на входе на страницу, не между
  шагами конструктора (§5.2).
- **`GET /me/trials/`** – список пробных родителя, уже готов и типизирован
  на бэке.
- **`/me/bookings/` (рабочее название)** – планируемый агрегирующий эндпоинт
  для UI-блока «Наши записи»: объединяет `Enrollment(type=TRIAL)` и
  `EventRegistration` родителя в один список, сортирует по дате, пагинирует
  тем же конвертом, что и галерея (`{count, next, previous, results}`).
  Модели на бэке при этом **не сливаются** – это чисто эндпоинт на чтение
  поверх двух существующих таблиц. См. `progress-tracker.md`.
- **Оплата ивентов не готова.** `POST /public/events/{id}/register/` сейчас
  создаёт гостевую бронь (`PENDING_PAYMENT`, оплата на месте, автоотмена
  через 30 минут) – это осознанное решение бэка, которое сейчас меняют на
  реальную онлайн-оплату. Не подключать оплату `/enroll/event`, пока
  `POST /checkout/event` не появится.

## 7. Рендеринг

`routeRules` в `nuxt.config.ts`:

| Роуты                                                                    | Режим                         | Почему                                     |
| ------------------------------------------------------------------------ | ----------------------------- | ------------------------------------------ |
| `/`, `/clubs`, `/gallery`, `/about`, `/teachers`, `/privacy`, `/consent` | `ssr: true`                   | Нужна индексация                           |
| `/enroll/trial`, `/enroll/event`, `/enroll/subscription`                 | `ssr: true`                   | –                                          |
| `/login`, `/me`                                                          | `ssr: false`                  | Личные данные, рендерить на сервере нечего |
| `/**`                                                                    | `ssr: true` + CSP `frame-src` | Виджеты VK / Яндекс / Turnstile            |

`prerender` не используется осознанно: страницы фетчат бэкенд, а на этапе
сборки (Docker, CI) его может не быть.

> ⚠️ `README.md` в корне всё ещё описывает `prerender` для `/about`,
> `/teachers`, `/privacy`, `/consent`. Устарело.

## 8. Инварианты

Нарушение любого пункта – повод откатить изменение, а не обсуждать.

1. **Сеть только через сервисы.** Ни `$fetch`, ни `useFetch` вне
   `app/services/*.service.ts`. Единственная точка транспорта – `useApi()`.
2. **`useApi()` и `useXService()` – только в setup-контексте.** Не внутри
   обработчиков, `watch` или методов классов.
3. **Один баррель типов** – `app/types/index.ts`. Второй файл типов не заводить.
   `app/types/api.d.ts` генерируется (`bun run schema:update`) и руками не правится.
4. **Маппинг DTO → доменная модель только в сервисе.** Компонент не видит
   snake_case-полей бэка.
5. **Ошибки API только через `parseApiError` / `getFetchStatus`.**
6. **Деньги только через `kopecksToRubles` / `formatRub`.**
7. **Токены только через `app/utils/auth-tokens.ts`.** Прямых обращений к
   `localStorage` за токенами нет.
8. **Цвета только через токены** `--ui-*` и утилиты Tailwind. Захардкоженных
   hex-значений в компонентах нет.
9. **Производное состояние – `computed`.** Не `watch`, пишущий в `ref`.
10. **Мутация пропсов запрещена.** Изменение – через `emit` или `defineModel`.
11. **`devtools` и `typescript.typeCheck` в `nuxt.config.ts` выключены осознанно**
    (память dev-сервера). Не включать.

## 9. Окружение и деплой

- **Переменные:** `NUXT_PUBLIC_API_BASE`, `NUXT_PUBLIC_TURNSTILE_SITE_KEY`.
  `.env` не коммитится, образец – `.env.example`.
- **Docker:** `docker-compose.yml`, `network_mode: host` (Linux) – SSR внутри
  контейнера и браузер ходят к бэку по одному адресу.
- **CI:** `.github/workflows/ci.yml` на каждый push:
  `format:check → lint → typecheck → build`.
- **Pre-commit:** husky, `prettier --write . && lint && typecheck`.

> ⚠️ Прод-хостинг, домен и процесс выкладки не описаны. Открытый вопрос.
