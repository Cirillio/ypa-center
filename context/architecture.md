# Архитектура фронтенда

Что и где живёт, кто с кем имеет право разговаривать, и какие правила нельзя
нарушать. Описывает **фактическое** состояние на 2026-09-30; расхождения с
желаемым помечены как ⚠️ и продублированы в `progress-tracker.md`.

## 2. Схема: слоистая

Проект использует **слоистую** архитектуру, не FSD. Решение зафиксировано:
доменов немного, команда — один человек, дробить на `features/entities` нет смысла.

Поток данных строго в одну сторону:

```
pages/ ──► composables/ ──► services/ ──► HTTP (useApi)
   │            │                │
   │            └──► stores/     └──► types/ (DTO → доменная модель)
   └──► components/ ──► utils/, constants/, app.config.ts
```

### Компоненты: группировка

`app/components/` – структура канонична для Nuxt 4 без плоского корня и без искусственной папки `app/`:

- **`layout/`** – каркас лейаута (`Header`, `Footer`, `MobileMenu` → `<LayoutHeader />`, `<LayoutFooter />`, `<LayoutMobileMenu />`).
- **`ui/`** – базовые визуальные кирпичики (`Photo`, `Video`, `ScrollFade`, `PageSection`, `SectionLeading`, `RoundIcon`, `RadioCard` → `<Ui* />`).
- **`promo/`** – сквозные конверсионные и маркетинговые секции (`Faq`, `JoinUs`, `Subscriptions`, `FloatCard` → `<Promo* />`).
- **Доменные подпапки** по страницам и флоу: `home/`, `clubs/`, `about/`, `teachers/`, `gallery/`, `me/`, `login/`, `enroll/` (`trial/`, `subscription/`, `event/`), `checkout/`, `feedback/`, `legal/`. Префикс имени компонента формируется Nuxt автоматически от имени папки.
- **Виджеты страницы:** крупный домен страницы делится на подпапки-блоки с корневым `Widget.vue` (секция: заголовок, скелетон, ошибка + `retry`, пустое состояние) и `Card.vue` (элемент списка). Так устроены `me/parent|subscriptions|bookings|upcoming/` и `login/otp|profile/` → `<MeBookingsWidget />`, `<LoginProfileWidget />`. Страница только собирает виджеты и отдаёт им данные.

### Декомпозиция внутри виджета: когда выносить подкомпонент

`Widget.vue` – точка входа секции: фетчит данные (`useXService`/composable),
держит `pending`/`error`, раскладывает подкомпоненты. Сам почти не рендерит
разметку. Внутри виджета (и на странице вообще) подкомпонент выносится
**обязательно**, если верно любое из условий – иначе не мельчить:

1. **Повторяется через `v-for`** → `Card.vue` / `Item.vue`. Разметку карточки
   инлайн в цикле внутри виджета или страницы не писать. Пример:
   `me/subscriptions/Card.vue`, `me/bookings/Card.vue`.
2. **Есть поля ввода + сабмит** (хотя бы одно поле с валидацией) →
   `Form.vue`, привязанный к Zod-схеме (`code-standards.md` §6), эмитит
   `submit`. `<form>`/`<UInput>` россыпью в шаблоне виджета или страницы –
   запрещено. Пример: `enroll/event/ContactsForm.vue`.
3. **Самостоятельный смысловой блок внутри виджета** – свой заголовок, своя
   часть пропсов/эмитов, мог бы существовать отдельной секцией, даже если
   данные не фетчит сам. Два разных по смыслу подраздела в одном шаблоне не
   сливать. Пример: `me/parent/Widget.vue` не рисует профиль и детей сам, а
   собирает `Info.vue` + `Children.vue`.
4. **Кластер действий с собственным состоянием** (подтверждение, модалка,
   набор кнопок с зависимым друг от друга `disabled`/`loading`) → отдельный
   компонент, не блок кнопок внутри виджета. Пример: `me/parent/LeaveConfirm.vue`.
5. **Используется в двух и более местах** → компонент выносится независимо
   от размера, в `ui/` или в доменную папку (общее для страниц записи – `enroll/`).

Что **не** выносится отдельно (обратная сторона – не мельчить): одиночная
кнопка без собственного состояния, одна строка текста, одна строка
«ключ – значение» в сводке.

### Ленивая загрузка компонентов (`<Lazy... />`)

- **Модалки, диалоги, формы с валидацией**, открывающиеся по клику: загружаются лениво с префиксом `Lazy` по паттерну Deferred Mount (`v-if="hasBeenOpened"`). Монтируются при первом открытии и сохраняются при закрытии (`hasBeenOpened = true`), чтобы не ломать плавную анимацию исчезновения `UModal` (fade-out/scale). Код их Zod-схем и разметки не попадает в начальный бандл страницы/футера.
- **Карточки в циклах `v-for` и основной контент секций**: импортируются синхронно (без префикса `Lazy`). Оборачивание легковесных карточек в `Lazy` без `v-if` – антипаттерн (порождает водопад сетевых запросов чанков после ответа API).
- **Медиа**: картинки и iframe используют нативный браузерный `loading="lazy"` внутри компонентов `UiPhoto` и `UiVideo`, обёртка в `Lazy` для них не нужна.

## 4. Слой данных

### Сервисы

Один класс на домен API. Конструктор принимает транспорт, фабрика отдаёт
экземпляр:

```ts
export class GalleryService {
    constructor(private readonly fetch: ApiFetch) {}
    getAll(): Promise<GalleryPhoto[]> { … }
}
export const useGalleryService = () => new GalleryService(useApi().apiFetch)
```

Почему так: `useApi()` и `useRuntimeConfig()` резолвятся только в
setup-контексте. Класс, получающий готовый `fetch`, не зависит от контекста
Nuxt и тестируется без него.

Сервисы автоимпортируются: `imports.dirs: ["services"]` в `nuxt.config.ts`.

### Запросы против мутаций

- **Чтение** – `useAsyncData(key, () => svc.method())` в странице или композабле.
- **Мутация** – метод сервиса, вызванный из композабла фичи
  (`useCallbackForm`, `useCabinetChildren`, `useEventCheckout`).

### Политика асинхронных данных

Сверено с докой Nuxt 4.4 («A note on `await`»): сервер дожидается каждого
`useAsyncData` независимо от `await`, HTML приходит заполненным. `await` меняет
только две вещи – код после вызова в `setup` и **блокировку перехода на клиенте**.

**Инструменты**

- `useAsyncData` + метод сервиса – единственный способ читать данные в компонентах.
- `useFetch` не используем: транспорт с токенами и refresh живёт в `useApi`,
  `useFetch` его обошёл бы.
- `$fetch` – только внутри `useApi` (и ротация токенов там же).

**`await`**

- Ставится, **только если код после него в `setup` нуждается в данных**:
  SEO-мета из сущности, `createError({ statusCode: 404 })` для несуществующей
  сущности. На 2026-09-28 таких мест нет – ни одного `await useAsyncData`.
- Ради SSR `await` не нужен и запрещён: он лишь замораживает старую страницу при
  переходе по клику.

**Классы данных**

| Класс         | Примеры                                           | Поведение                                                                                 |
| ------------- | ------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Основные      | каталог `/clubs`, педагоги, галерея, афиша записи | в SSR-HTML; при клиентском переходе – скелетон секции; ошибка – `UiErrorState` с повтором |
| Вторичные     | секции главной, расписание недели                 | в SSR-HTML; скелетон; ошибка – деградация в пустое состояние/CTA, страница живёт          |
| Только клиент | всё, что требует токена (`/me`, дети в чекауте)   | `server: false`; решение «гость/родитель» только после монтирования                       |

На клиент ради «быстрее» ничего не переносится.

**Состояния загрузки**

- Глобально – `<NuxtLoadingIndicator>` в `app.vue` (чанки, middleware).
- Секция сама показывает скелетон по `status === "pending"` своего запроса и
  **только пока данных нет** (`pending && !items.length`) – при `refresh` старые
  данные остаются на экране.
- Виджет смотрит только на свой `pending`, общий флаг «что-то грузится» на всю
  страницу не заводится.

**Ключи**

- Формат `<домен>[:<ресурс>][:<параметры>]`: `activities`, `events`,
  `schedule:week:2026-09-28`, `trial-slots:3`, `me-profile`.
- Один ключ = один запрос с одним смыслом. Одинаковый вызов сервиса в разных
  местах – один ключ (общие `data`/`status`, `clearNuxtData` сбрасывает всё).
  Разные параметры – разные ключи; эндпоинт сам по себе не повод объединять.
- Реактивный параметр – в ключ (getter) и в `watch`.

**Зависимые запросы и гидрация**

- Параметр зависимого запроса берётся из исходника (query, prop), а не из
  результата другого запроса, если это возможно: запросы идут параллельно, ключ
  известен уже в `setup` на сервере.
- Выбор, валидируемый по загруженному списку, – `computed` от «запрошенного» id
  и списка, а не `watch`, который его чинит: на сервере `watch` на догрузку не
  реагирует, и SSR расходится с клиентом (`useEventCheckout`, `useTrialCheckout`).
- Состояние, которое нельзя знать на сервере (токены, localStorage), выставляется
  в `onMounted`.

### Маппинг DTO

Внутри сервиса, не в компоненте. Сырые DTO – алиасы из `api.d.ts`
(`Profile`, `SubscriptionView`), доменные модели – без суффиксов
(`MeProfile`, `MeSubscription`, `PlanTier`, `WeeklySlot`). Суффикс `VM` не
используется.

### Фолбэк на конфиг

Часть данных дублируется в `app.config.ts` на случай недоступности API – так
устроен `useSubscriptionPlans` (`/public/plans/` → фолбэк на
`appConfig.subscriptions`). Форма фолбэка обязана совпадать с доменной моделью,
иначе шаблоны разъедутся.

### Ошибки

Бэк отдаёт RFC 9457 (`ProblemDetail`). Всё разбирается в `app/utils/parse-error.ts`:
текст – `parseApiError(err, fallback)`, машинный код – `getProblemCode(err)`,
статус – `getFetchStatus(err)`. Ветвление по бизнес-ошибкам – **только по `code`**
(`type`/`title` строятся из имени класса исключения и меняются при рефакторинге
бэка). Тело проверяется type guard'ами, не `as`. Свои парсеры не писать.

`403 PROFILE_INCOMPLETE` перехватывает транспорт `useApi` (редирект на анкету,
ошибка всё равно пробрасывается) – виджеты этот случай не обрабатывают.

### Пагинация списков

Бэк пагинирует списки через `?limit&offset` (без `limit` – голый массив). Сервис
возвращает `Page<T>` с уже смапленными `results`, композабл `usePagedList`
держит первую страницу в `useAsyncData` и дописывает следующие по «Показать ещё».
`useShowMore` остаётся для коротких клиентских списков (лента «Ближайшие»).

### Деньги

Бэк отдаёт копейки. `kopecksToRubles(k): number` – для доменной модели,
`formatRub(k): string` – для прямого вывода копеек из DTO, `formatRubles(r): string` –
для вывода уже рублёвого поля доменной модели. Все три в `app/utils/format-price.ts`.
Делить на 100 вручную запрещено. `formatRub` на рублёвом поле занижает цену в 100 раз
(баг «Наших записей» 2026-09-24).

## 5. Аутентификация, регистрация и доступ

Беспарольный вход по OTP на email. Полные правила и антиспам – `backend/auth-flow.md`
(авторитет), здесь – как это ложится на фронт.

### 5.1 Принцип: один флоу на вход и на регистрацию

Отдельной формы регистрации **нет**. Есть один экран `email → код`, а дальше
бэк решает по состоянию профиля:

```
email → [код на почту] → verify (доказано владение почтой)
  │
  ├── профиль пуст (первый вход) → показать анкету (ФИО, телефон, «откуда узнали»,
  │     согласие на обработку ПД)
  │     └── пока анкета не заполнена – в кабинет/checkout не пускать;
  │         при следующем входе анкета покажется снова (не начинать заново)
  │
  └── профиль заполнен → сразу в кабинет / на целевую страницу
```

`Parent` создаётся на бэке ровно на `verify`, с одним известным полем –
email. Анкета досылается отдельным шагом, `PATCH /me/profile/`. Бросить
на анкете и вернуться позже – нормально, не «битая» запись: бэк узнаёт email
через `get_or_create` и просто продолжает с того же места.

**Теневая регистрация explicitly отклонена** как архитектурное решение бэка
(`backend/auth-flow.md` §1.4: раньше при покупке пробного бэк создавал `Parent`
в фоне без подтверждения почты – убрано как источник хрупкости). Не
реализовывать на фронте ничего похожего – учётка появляется только через
доказанное владение email.

**Реализация на фронте** (2026-09-24):

- Анкета – шаг `profile` стора `auth` на той же странице `/login`
  (`LoginProfileWidget`). Шаг после `verify` выбирается по `profile_completed`
  из ответа verify, без отдельного запроса профиля. Переход на `/me` после
  анкеты делает страница, а не композабл, и сбрасывает кэш `me-profile`.
- Поля: ФИО, телефон (полная маска), «откуда узнали» (enum бэка
  `ReferralSourceEnum`, подписи – `constants/referral-sources.ts`), **согласие
  на обработку ПД – обязательный чекбокс** `UiConsentCheckbox`. Все обязательны:
  без любого из них бэк не считает анкету заполненной. Почта – подтверждённая,
  только для чтения, в payload не входит.
- Всё уходит в `PATCH /me/profile/` (`full_name`, `phone`, `referral_source`,
  `pd_consent: true`).
- Валидация только при сабмите (`validate-on="[]"`), ошибка поля снимается при
  его изменении (`form.clear(name)`), фокус – на первое ошибочное поле.
- Критерий «анкета заполнена» – флаг бэка `profile_completed`, изолирован в
  `isProfileComplete` (`me.service.ts`).

### 5.2 Кто куда попадает без сессии

| Действие                              | Авторизация               | Поведение без сессии                                    |
| ------------------------------------- | ------------------------- | ------------------------------------------------------- |
| Запись на **событие**                 | Не нужна                  | Полностью анонимно, `parent_id = null`                  |
| Конструктор **пробного**              | Не нужна для выбора слота | Выбор ребёнка и чекаут требуют входа (кнопка неактивна) |
| Конструктор **абонемента**            | Не нужна для выбора слота | Выбор ребёнка и чекаут требуют входа (кнопка неактивна) |
| Личный кабинет (`/me`)                | Обязательна               | `middleware: "auth"` → редирект на `/login`             |
| Результат оплаты (`/checkout/result`) | Обязательна               | `middleware: "auth"` → `/login?redirectFrom=...`        |

`redirectFrom` живёт в query страницы `/login` и переживает все шаги входа
(email → код → анкета, если нужна): шаги – состояние стора `auth`, страница не
меняется. После входа `login.vue` возвращает на исходную страницу.
**Принимается только внутренний путь из белого списка** – открытый редирект
иначе. Проверка – `resolveRedirect` (`app/utils/resolve-redirect.ts`): белый
список по `pathname` (`/me`, `/enroll/trial`, `/enroll/subscription`, `/checkout/result`), query
сохраняется, hash отбрасывается, всё остальное (внешний URL, `//host`, `\`,
не строка, путь вне списка) даёт `/me`. Корзины/сохранения состояния конструктора покупки нет – ушёл со
страницы, собираешь заново (`backend/checkout-flow.md` §1, §4).

### 5.3 Антиспам/флуд (только частотные лимиты, без капчи)

- Код нельзя запрашивать чаще раза в 60 секунд на один email.
- Не больше 5 запросов кода в час на email и отдельно на IP.
- Не больше 5 попыток ввода кода – дальше код сгорает, нужен новый запрос.
- `POST /auth/otp/request/` отвечает одинаково (`202`) вне зависимости от
  того, существует email или нет – по ответу нельзя узнать, зарегистрирован
  ли человек.
- Это серверные лимиты (throttling); Turnstile на OTP не стоит – она только
  на публичных формах обратной связи и звонка.

### 5.4 Токены

- **Хранилище:** `localStorage`, ключи `ypa_access` / `ypa_refresh`.
  Доступ только через `app/utils/auth-tokens.ts`.
- **Сроки:** access 15 минут, refresh 30 дней с ротацией.
- **Перехват 401:** в `useApi()`. Single-flight refresh (один общий
  `refreshPromise`), затем ровно один повтор исходного запроса. Эндпоинты
  `/auth/token/refresh/`, `/auth/otp/`, `/auth/logout/` из перехвата исключены.
- **Провал refresh:** токены чистятся, стор сбрасывается, редирект на `/login`.
- **Гейт роутов:** `middleware/auth.ts`. Источник истины – `hasTokens()`
  (читает `localStorage`), `store.hydrate()` подтягивает к нему флаг `isAuthed`.
- **Гейт «профиль заполнен»:** не в middleware, а в данных страницы – `/me`
  при `isComplete === false` уводит на `/login`, `/login` при заполненном
  профиле уводит на `/me`. Middleware остаётся дешёвым (без запроса профиля).
- **Стор `auth`:** держит только состояние OTP-флоу (email, code, step, таймер)
  и флаг `isAuthed`. Профиль пользователя в сторе не лежит – он грузится
  композаблом `useMeProfile`.

**Несколько вкладок.** Токены общие (`localStorage`), сессию синхронизируют два механизма:

- Плагин `plugins/auth-sync.client.ts` слушает `storage` по ключу access
  (`isAccessTokenKey`) и реагирует только на **смену статуса сессии**, а не на
  ротацию access. Выход в другой вкладке сбрасывает флоу и уводит с экрана за
  гейтом `auth` на `/login`. Вход в другой вкладке переводит вкладку с `/login`
  тем же путём, что и `onMounted` страницы: проверка профиля, `resolveRedirect`.
- Ротация refresh в `useApi.ts` идёт под замком Web Locks (`ypa-token-refresh`).
  Бэк ротирует refresh и сразу блэклистит старый (`ROTATE_REFRESH_TOKENS`,
  `BLACKLIST_AFTER_ROTATION`), поэтому две вкладки с одним refresh сожгли бы токен
  друг друга и разлогинили пользователя везде. Вкладка, дождавшаяся замка, видит в
  хранилище access, отличный от того, с которым получила 401, и берёт уже
  обновлённую пару без запроса. Single-flight внутри вкладки остаётся. Без Web
  Locks (старые браузеры) поведение прежнее.

**Конструкторы открыты гостю** (решение владельца 2026-09-30): выбор кружков и
слотов на `/enroll/trial` и `/enroll/subscription` доступен без входа. Барьер –
на сабмите: без сессии ребёнка не выбрать, «Продолжить» неактивна, а
`useCheckoutPayment` дополнительно уводит на `/login?redirectFrom=…`. Гейт
профиля обеспечивает бэк (`403 PROFILE_INCOMPLETE` → перехват в `useApi`).
Экран `/checkout/result` закрыт `middleware: "auth"`.

## 6. Чекаут и бронирования

Контракты снятые с бэка на ветке `def` (`backend/api-core-contracts.md`,
`backend/checkout-flow.md`) – сюда только то, что напрямую бьёт по фронту.

- **Поток оплаты** (реализован 2026-09-30, отчёт – `tasks/payment-checkout/report.md`):
  страница собирает тело заказа `computed` (`null` при неполном выборе) →
  `useCheckoutPayment` → `BillingService` → `POST /checkout/{subscription,trial}`
  (пути без завершающего слеша). `payment_url` → ЮKassa **в той же вкладке**;
  `CONFIRMED` без `payment_url` (депозит покрыл всё, бесплатное пробное) → сразу
  `/checkout/result?tx=`. Вариант с новой вкладкой отклонён владельцем.
- **`X-Idempotency-Key`** – производное от отпечатка состава заказа
  (`utils/order-fingerprint.ts`): тот же состав – тот же UUID (повтор после сбоя
  сети и «назад» с ЮKassa не создают второй заказ), другой состав – новый.
  Ключ живёт в замыкании композабла, без `watch`. `IDEMPOTENCY_KEY_REUSED`
  сбрасывает отпечаток, автоповтора нет – он скрыл бы баг ключа.
- **Ошибки чекаута** – только по `code`: тексты в `useCheckoutPayment`,
  `NOT_FOUND` / `NO_AVAILABLE_SEATS` и ошибка по полю `trial_date` («занятие уже
  началось») перезапрашивают слоты, `FORBIDDEN_RESOURCE` – детей (колбэки
  `onSlotsStale` / `onChildrenStale` от страницы). Пауза кнопки – `Retry-After` через
  `getRetryAfter`. Под ошибкой – короткий код обращения из `request_id`.
- **Депозит в чекауте** – `useCheckoutDeposit`: баланс только родителю и после
  монтирования (гостю запрос дал бы `401` и уход на `/login`), ключ `me-deposit`
  общий с кабинетом, списание `min(баланс, цена)` – та же формула, что на бэке.
  У пробного `use_deposit` нет.
- **Экран результата** `/checkout/result?tx=` (`ssr: false`, `middleware: "auth"`):
  `useTransactionStatus` опрашивает `GET /checkout/transactions/{id}` раз в 2 с,
  пока `PENDING`; дедлайн – `expires_at` + 5 минут (до первого ответа – 60 с),
  `403`/`404` терминальны, сеть и 5xx ждут в пределах дедлайна. Шесть состояний –
  `CheckoutResultWidget`: ожидание, успех (чек из `order`), отмена, возврат
  (`constants/refund-reasons.ts`), таймаут («обновите страницу»), не найден. Без `tx` –
  экран «Вы вернулись из банка». «Попробовать снова» – новая покупка с новым ключом.
- **Результат оплаты события** – тот же экран с `?tx=…&kind=event` (`return_url` бэка),
  **без входа**: платит гость. Страница объявляет `definePageMeta({ authSkip })` –
  предикат по маршруту; `middleware/auth.ts` пропускает гостя, если предикат истинен.
  Разбор `kind` – `parseCheckoutResultKind` (`event` | `purchase`, всё прочее – `purchase`).
  Статус – публичный `GET /public/events/payments/{id}/` (без ПД) через
  `BillingService.getEventPaymentStatus`; `useTransactionStatus(txId, kind)` выбирает
  источник, логика опроса общая. `order` доменной `CheckoutTransaction` – размеченное
  объединение `purchase` | `event`; чек и кнопки виджета ветвятся по `order.kind`.
- **Абонемент:** в заказ уходят `schedule_id` слотов (паттерн «ПН 16:00»), не
  календарные даты. Тариф не выбирается – выводится из числа слотов; тариф из
  фолбэка `app.config` без `id` оплатить нельзя.
- **Пробное:** выбор кружка → свободный календарный слот из
  `GET /public/activities/{id}/next-slots/` (сегодня + 13 дней, только со
  свободными местами, без счётчика мест). У слота нет `id` – ключ
  `${scheduleId}_${date}`, в заказ уходят `schedule_id` и `trial_date`.
- **Конструкторы открыты гостю**, барьер – на сабмите (§5.2).
- **`/me/bookings/`** – «Наши записи»: пробные и регистрации на события одним
  списком. Фронт всегда запрашивает `period=all` – бэк сам ставит предстоящие по
  близости, затем прошедшие от свежих; виджет лишь вставляет заголовок
  «Прошедшие» перед первой `isPast`. Модели на бэке **не сливаются** – это
  эндпоинт на чтение поверх двух таблиц. `GET /me/trials/` устарел и не
  используется.
- **Депозит** – баланс на кнопке в шапке кабинета (`MeDepositWidget`), история
  движений – в поповере, грузится при первом открытии.
- **Удаление ребёнка** – мягкое (`DELETE /me/children/{id}/`). При `409` окно
  подтверждения показывает живые записи из `extensions.active_enrollments`
  вместо кнопки «Удалить».
- **Бронь события** (`/enroll/event`): `useEventRegistration` → `EventsService.register` →
  `POST /public/events/{id}/register/` без входа. Бесплатное событие бэк подтверждает
  сразу (`201 {status: "accepted"}`), платное с 2026-10-05 (бэк PR #31) оплачивается
  онлайн: ответ как у чекаута (`transaction_id`, `payment_url`, `expires_at`). Сервис
  различает ответы и отдаёт доменное объединение `EventRegistrationOutcome`
  (`accepted` | `payment`) – компоненты форму DTO не разбирают. Ошибки полей – по
  `invalid_params`, остальное – по `code`. Страница показывает только будущие события
  (`is_upcoming`). Отдельного `POST /checkout/event` нет.
- **`X-Idempotency-Key` брони события** – только у платного события (бесплатному бэк
  ключ не требует). Тот же принцип, что у чекаутов: ключ из отпечатка формы
  (`createEventOrderFingerprint` в `utils/order-fingerprint.ts`: событие, места,
  телефон в E.164, email и имена без пробелов по краям). Та же форма – тот же ключ,
  изменилась – новый. Бэк солит отпечаток телефоном брони, а не родителем: гость без входа.

## 8. Инварианты

Нарушение любого пункта – повод откатить изменение, а не обсуждать.

1. **Сеть только через сервисы.** Ни `$fetch`, ни `useFetch` вне
   `app/services/*.service.ts`. Единственная точка транспорта – `useApi()`.
2. **`useApi()` и `useXService()` – только в setup-контексте.** Не внутри
   обработчиков, `watch` или методов классов.
3. **Один баррель типов** – `app/types/index.ts`. Второй файл типов не заводить.
   `app/types/api.d.ts` генерируется (`bun run schema:update`) и руками не правится.
4. **Маппинг DTO → доменная модель только в сервисе.** Компонент не видит
   snake_case-полей бэка.
5. **Ошибки API только через `parseApiError` / `getFetchStatus`.**
6. **Деньги только через `kopecksToRubles` / `formatRub` / `formatRubles`.**
7. **Токены только через `app/utils/auth-tokens.ts`.** Прямых обращений к
   `localStorage` за токенами нет.
8. **Цвета только через токены** `--ui-*` и утилиты Tailwind. Захардкоженных
   hex-значений в компонентах нет.
9. **Производное состояние – `computed`.** Не `watch`, пишущий в `ref`.
10. **Мутация пропсов запрещена.** Изменение – через `emit` или `defineModel`.
11. **`devtools` и `typescript.typeCheck` в `nuxt.config.ts` выключены осознанно**
    (память dev-сервера). Не включать.
